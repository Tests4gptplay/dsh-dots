# DSH Dots 1.0.12-review.3 — 既有安装身份恢复

## 原因与现象

正式 GitHub Release `v1.0.11` 的包名、`cordis.patch.yml` 模块名和客户端模块注册名均为 `dsh-dots`。
后续源码候选错误地将上述身份直接改为 `@tests4gptplay/dsh-dots`；当已安装 `dsh-dots` 的 DSH 再安装该候选时，包管理器可以把它作为第二个依赖而非原包升级，造成两个 Dots 安装条目。

## 修改

- 将 GitHub 源码包身份恢复为 `dsh-dots`（`package.json`、`cordis.patch.yml`、编译后的客户端注册 ID）。插件 UI 行 ID 仍为 `dsh-dots`。
- `scripts/build.mjs` 从当前清单自动读取模块名并生成客户端运行文件，不再在生成脚本中硬编码另一包名。
- 更新真实安装所使用的本地 npm/pnpm CI 用例，增加 `tests/package-identity.test.mjs`，确保三个安装身份继续与 `v1.0.11` 对齐。
- 保留已有的 `scripts/npm/prepare-scoped-npm.mjs`：它从未改名的 GitHub 源码生成单独的 `@tests4gptplay/dsh-dots` npm 发行包，独立调整发行清单、Cordis 引用和客户端注册 ID。发布工作流仍需单独授权，当前未发布新的 npm 包。
- 本轮未更改 Dots 网页、登录态修复器、MCP、DSH 安装或用户配置。

## 验证

- **复现**：原候选在新增 `tests/package-identity.test.mjs` 下失败，显示实际 `@tests4gptplay/dsh-dots` 与正式版的 `dsh-dots` 不一致。
- **修复**：Node 22.16 / 隔离环境 `npm test`：50 通过、0 失败、0 跳过。
- `npm run pack:check`：13 个生产文件，白名单通过。
- `npm pack` 得到 `dsh-dots-1.0.12-review.3.tgz`，SHA-256 `a976c66f614219f8f0a577c4af9acc43315057fa7c4fa5dbaefaf035f81d4c9d`；解包核对清单与 `cordis.patch.yml`、客户端注册身份一致。
- 对离线临时项目安装此 TGZ 后，`import('dsh-dots')` 与 `import('dsh-dots/package.json')` 成功，读取的版本为 `1.0.12-review.3`。
- GitHub Actions：本分支需完成 Windows/Ubuntu 测试与 scoped npm 包构建检查；其具体结果以该提交对应的 CI 记录为准。

## 安装与验收

升级原正式 GitHub 安装的 `dsh-dots`，使用本测试分支 `github:Tests4gptplay/dsh-dots#test/login-retention-1.0.12` 或本轮 `dsh-dots-1.0.12-review.3.tgz`。

之前错误安装的 `@tests4gptplay/dsh-dots@1.0.12-review.2` 属于另一个包身份；清理这一额外条目时，只移除该额外安装记录，保留原 `dsh-dots` 与用户配置、登录资料。此后同一 GitHub 安装身份可以连续升级。
